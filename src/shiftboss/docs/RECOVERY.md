# 中断与会话恢复

恢复由事件触发，调用现有 `recover`；不靠派活方读日志后手动敲「继续」。

| 事件 | 自动行为 |
| --- | --- |
| `SessionStart`（startup、resume、clear、compact） | 登记的甲方检查并接回意外退出的后台任务 |
| `UserPromptSubmit`（含门铃、心跳） | 先按既有规则认领甲方，再触发恢复，补偿宿主未发恢复事件的情况 |
| `Interrupt` | 检查其他后台任务；不重启被用户中断的主轮次，不阻止用户停止 |

## 安装

在被管理项目使用同一虚拟环境的 Python：

```sh
python -m shiftboss.hooks.auto_recover --repo /absolute/project --install-hooks /absolute/workspace/.codex/hooks.json
```

安装幂等，保留已有 Stop 与其他处理器。已有认领处理器由包含相同认领步骤的恢复入口接替，避免依赖不同 hook 的执行顺序。安装只写指定的 hooks.json，不修改宿主的 hook 信任记录。Codex 首次加载新增或变更的 hook 若要求信任审核，按宿主提示审核；不得绕过信任检查。甲方首次认领前不自动恢复，执行副本也不能触发此入口。

安装后的事件处理器只启动独立后台恢复作业，不在 Interrupt 的三秒限制里等待执行方启动。宿主未实际加载或信任 hook 时，不能报告自动触发已生效；可分别查看配置、宿主事件和下述运行记录。

## 唯一恢复规则

继续使用收件箱的 `session_state`，不再从错误文字、未推送时长或终端存活推断任务完成：

- `进程已退出`、结构化错误导致的 `执行中断`：原任务、原会话执行 `dispatch --recover`，保留历史与未提交文件。
- 正常运行、已正常完成或已交回待核对、`--close`、用户取消：跳过。等待前置的关闭会话不自动续派。
- 常驻仅旧锁仍在、进程消失且没有 stop 请求时恢复；三个支线分别处理，不用一个 start 顺带复活主动停止的其他支线。没有锁或开关关闭时保持原样。

事件入口与人工 `recover` 共用操作系统独占锁，崩溃自动释放。重复事件不并发恢复；同一分钟的顺序重放跳过。失败后保留真实退出码，在下一次事件到达且超过一分钟时再尝试，没有自动紧密重试循环。恢复时再次检查甲方身份与 `[automation] session_recover`，开关关闭即不执行。

## 自动接受标准

`tests/test_auto_recover_hooks.py` 与 `tests/test_session_failure_recovery.py` 固定验证：事件确实调用恢复、原会话与脏文件保持、完成和用户取消不恢复、身份和目录边界、重复事件与手工入口互斥、失败可见且后续限频重试、主动停机不复活、安装幂等且保留其他 hook。

运行事实保存在控制目录：`auto-recover.json` 记录触发事件、PID、开始、结束与退出码；`auto-recover.log` 保留恢复命令的真实输出，超过 2 MB 轮换上一份。失败同时进入简报。`completed` 只说明本轮恢复命令成功，不证明产品、任务验收或页面通过。
