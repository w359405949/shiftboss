# 中断与会话恢复

恢复由事件触发，调用现有 `recover`；不靠派活方读日志后手动敲「继续」。

闭包命令失败时，`regen` 将本次完整 stdout／stderr、实际命令、源码提交与退出码保存到
`control/verification/closure-failures/<唯一运行目录>/result.json`，日志使用项目输出协议。
没有 origin 的独立源码目录写入自身 `out/generation-checks/closure-failures/`。
报错同时显示首段与尾段并引用该原件；先读该次原件定位首错误，不凭下游 JSON 尾栈猜因，
也不为恢复已保存的输出重新执行整条闭包。后续失败使用新目录，不覆盖旧结果。
超时同样保存终止前已取得的原始字节；记录 `timed_out`、实际超时秒数，退出码为 null，
不把超时拼成内层 Error、虚构退出码或通过。预览的解码替代不改动保存的原始输出。

## 压缩后的规则与当前工作

阶段性的目标、优先级与检查取舍放在甲方私有 `control/PHASE.md`，不放项目架构文档，
也不在多份任务书中复制。派活方维护当前一份原件，阶段结束时替换、清空或删除；
任务进度和待办仍由原台账管理，派发时只把相关要求转为本任务的具体目标。
文档首行用标题，另写 `目标：一句话`，正文写工作取舍、完成边界与停止条件。
阶段由派活方持续维护：用 `重心：一句话` 概括当前整体在推进什么，
`当务之急：一句话` 写眼下最优先的事，让用户能及时发现跑偏，并提醒压缩后的派活方。
整体重心或优先事项实质变化时同步更新，不从任务数量或红绿票自动推断，
不让逐项技术报告淹没阶段摘要。简报有重心时优先显示重心，未写时仍显示目标。
可加 `进度：约 30%（估算）`、`更新时间：2026-11-09 23:57 +08:00`、`依据：估算所据的实际里程碑与未完项`。
进度写清所指阶段、口径与估算性质，不能用派发数、合入次数或旧阶段完成率代替当前阶段完成率。
每次根据实质进展重估时同步修改进度、绝对时间（含时区）与依据；阶段切换时重新确定口径。
缺少同口径复验时明确估算不确定性，不伪称已经测得错误消除比例。
简报在前部显示阶段标题、目标、可选进度及其原更新时间、依据与原件入口；
读取简报、修改其它正文或收到重复门铃都不自动刷新进度时间。进度缺时间时明确显示未填写，
不拿文件修改时间或简报生成时间充数。阶段原件读取失败明确显示，不沿用旧目标。

Codex 的 `SessionStart` 在 `source=compact` 时于压缩后的下一次模型请求前运行，
`source=resume` 对应恢复会话。上下文刷新与异常任务恢复是两个处理器：前者重读规则，
后者接回异常退出的任务，互不以对方成功作为验收结论。

```sh
python -m shiftboss.hooks.context_refresh --repo /absolute/project --install-hooks /absolute/workspace/.codex/hooks.json
```

安装幂等并保留现有处理器，只在 `compact|resume` 上运行；不同时登记 `PostCompact`，
以免一次压缩重复注入。范围限定为已认领甲方及项目根或父目录，执行副本不读取甲方私有状态。
处理器每次先从磁盘读取并完整注入 `control/PHASE.md`，再读取 `AGENTS.md`、项目 `README.md` 和协作规则第 2.1、5.1、2.0、4.3 节，
将原文与未关闭任务的当前任务书入口、待办及正常验证阶段一并作为 `additionalContext` 返回。
不另外维护手写交接摘要，不扫描历史会话、归档日志或运行耗时收件箱。

恢复后的首个工作步骤须读当前相关任务的合同、最新轮次与交回，并用 `inbox list`、`brief`
核对实际现场后再合并、派发、归档或清理。台账未关闭不等于实际执行，阶段快照不代表产品通过；
最新用户指令优先，旧门铃按当前台账去重。尚未注入的文档、缺失章节与读取失败明确列出，
不切掉半条规则，也不把读不到当作没有约束。阶段文档超出输出预算时只保留入口并要求先读全文，
不使用截断的阶段策略；执行副本不会得到甲方私有阶段文档。

上下文输出上限为 16000 UTF-8 字节，宿主设置有限的 `additionalContextLimit`；
超出部分保留权威入口，相关操作前再读取，避免把整个历史重新放回上下文。
`control/context-refresh.json` 只记录事件、文件身份和未完整注入项，`emitted` 仅表示处理器已输出，
不证明宿主实际加载或模型已遵守。安装不修改 hook 信任记录；尚未获宿主信任时不能报自动生效。
有限验收见 `tests/test_context_refresh_hooks.py`：压缩／恢复触发、实时重读、角色隔离、
状态损坏可见、输出有界与幂等安装均须成立。

事件协议依据：[OpenAI Hooks 文档](https://learn.chatgpt.com/docs/hooks)。

## 自动任务恢复事件

| 事件 | 自动行为 |
| --- | --- |
| `SessionStart`（startup、resume、clear、compact） | 登记的甲方检查并接回意外退出的后台任务 |
| `UserPromptSubmit`（含门铃、心跳） | 先按既有规则认领甲方，再触发恢复，补偿宿主未发恢复事件的情况 |
| `Interrupt` | 检查其他后台任务；不重启被用户中断的主轮次，不阻止用户停止 |

## 安装

在被管理项目使用同一虚拟环境的 Python：

```sh
python -m shiftboss.hooks.auto_recover --repo /absolute/project --install-hooks /absolute/workspace/.codex/hooks.json
```

安装幂等，保留已有 Stop、认领与其他处理器。自动入口内先完成既有认领步骤，避免依赖不同 hook 的执行顺序；保留原认领处理器，让新增 hook 尚未获信任时仍能正常认领。安装只写指定的 hooks.json，不修改宿主的 hook 信任记录。Codex 首次加载新增或变更的 hook 若要求信任审核，按宿主提示审核；不得绕过信任检查。甲方首次认领前不自动恢复，执行副本也不能触发此入口。

安装后的事件处理器只启动独立后台恢复作业，不在 Interrupt 的三秒限制里等待执行方启动。宿主未实际加载或信任 hook 时，不能报告自动触发已生效；可分别查看配置、宿主事件和下述运行记录。

## 唯一恢复规则

继续使用收件箱的 `session_state`，不再从错误文字、未推送时长或终端存活推断任务完成：

- `进程已退出`、结构化错误导致的 `执行中断`：原任务、原会话执行 `dispatch --recover`，保留历史与未提交文件。
- 正常运行、已正常完成或已交回待核对、`--close`、用户取消：跳过。等待前置的关闭会话不自动续派。
- 消息投递未确认且插件仍确认执行中断时，可用 `dispatch <任务书> --recover --restart-interrupted` 重建故障终端并续原会话；拒绝正常运行、正常停靠、已关闭或副本不一致的线，保留工作树、会话号与轮次。
- 故障终端重建会结束该终端及其子命令；子命令按恢复中取消、结果未完成记录，不当作超时、检查通过或源码接受。
- 常驻仅旧锁仍在、进程消失且没有 stop 请求时恢复；三个支线分别处理，不用一个 start 顺带复活主动停止的其他支线。没有锁或开关关闭时保持原样。

事件入口与人工 `recover` 共用操作系统独占锁，崩溃自动释放。重复事件不并发恢复；同一分钟的顺序重放跳过。失败后保留真实退出码，在下一次事件到达且超过一分钟时再尝试，没有自动紧密重试循环。恢复时再次检查甲方身份与 `[automation] session_recover`，开关关闭即不执行。

## 自动接受标准

`tests/test_auto_recover_hooks.py` 与 `tests/test_session_failure_recovery.py` 固定验证：事件确实调用恢复、原会话与脏文件保持、完成和用户取消不恢复、身份和目录边界、重复事件与手工入口互斥、失败可见且后续限频重试、主动停机不复活、安装幂等且保留其他 hook。

运行事实保存在控制目录：`auto-recover.json` 记录触发事件、PID、开始、结束与退出码；`auto-recover.log` 保留恢复命令的真实输出，超过 2 MB 轮换上一份。失败同时进入简报。`completed` 只说明本轮恢复命令成功，不证明产品、任务验收或页面通过。
