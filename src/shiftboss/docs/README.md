# 代理协作工作流

Git Feature Branch Workflow：派活方负责初步检验、合并与派发，后台设施按第 3.0 节启停。**红不阻断合并。**
本文档只写规则；项目专有内容见项目文档，工具细节见工具自身。
身份由用户或派发指定：派活方是用户指定承担派活的会话；执行方是 `shiftboss dispatch` 派出、在任务书「你的工作副本」里工作的会话。未被指定身份的读者两方都不是，不按第 3、4 节行事。

**派活方先守两条：** 需要用户决定或补充的事，登记到简报后继续推进主线，不调用交互式问答工具等回复；验收只做基本、快速的检查，耗时细查写成脚本交后台运行，或单开核对线，不占住合并与派发。下文的核对、复现、反证与确认均按这两条执行。

## 0. 工具

本目录由 `shiftboss` 包安装进项目顶层 `shiftboss/`，不在此处修改（同目录的 `plans/` 是任务书，不属于装入的文件）；改动在包内 `docs/` 做，`shiftboss bootstrap` 同步，`--check` 报出不一致。
项目专有的约定（架构依据、术语、测试目录、证据目录、完成标准的不放松清单）见项目 `README.md` 指向的项目文档；文档写法见第 7 节。
家目录：项目旁的 `<项目名>.shiftboss/`（`shiftboss.toml` 的 `copies_dir` 可改），放 bare 仓库 `hub.git`、全部执行方副本（`<执行方><序号>`）与验证工作区 `verify/`。
控制目录：家目录下的 `control/`（`shiftboss.toml` 的 `control_dir` 可改），放仅派活方读写的私有文档（执行方评估 `EXECUTORS.md`、错题本 `mistakes.md`）、台账、配额、门铃与验证报告；工作副本内不存放、不链接。**例外**：执行方可只读其中 `verification/` 的日志与筛查，用于修认领给本线的红；`triage` 任务书的执行方另可只读 `patrol/` 的状态与日志。

| 入口 | 用途 |
| --- | --- |
| [`TEMPLATE.md`](TEMPLATE.md)、[`templates/`](templates/) | 任务书格式与各子类型骨架 |
| [`DONE.md`](DONE.md) | 完成标准：段内能做什么、怎么算做成 |
| `shiftboss taskbook` | 建、查、迁移任务书；任务书结构只由它解析 |
| `shiftboss dispatch` | 派活、写入交代、关会话、设配额 |
| `shiftboss inbox` | 各线状态与验证状态的唯一来源 |
| `shiftboss merge` | 合并；`--done` 关会话并归档 |
| `shiftboss verify` | 常驻验证：生成、全量测试、打包、归因、报红 |
| `shiftboss recover` | 拉起该在执行而进程没了的线；派活方会话恢复时由钩子跑 |
| `shiftboss bell` | 推送通知 |
| `shiftboss bootstrap` | 准备 bare、工作副本、钩子与本目录文档 |
| `shiftboss regen` | 按阶段生成：只跑输入改动的阶段及其下游，`--full` 为完整生成；产物名单由生产端经 `shiftboss.outputs` 声明 |

## 1. 对应关系

| 标准流程 | 本工作流 |
| --- | --- |
| issue | 任务书 `shiftboss/plans/<动词>-<对象>/` |
| feature branch | `codex/<任务书名>` |
| checkout | 工作副本，一份任务书独占一个 |
| pull request | 交回 `delivery.md` |
| code review | 核对：派活方做基本快速检查，细查交后台或核对线 |
| CI | 常驻验证 |
| 关闭 issue | 归档至 `shiftboss/plans/archive/` |

### 1.1 任务书

| 文件 | 内容 | 写权 |
| --- | --- | --- |
| `meta.json` | 表头事实 | 只经工具修改 |
| `contract.md` | 合同，含「派发与交付」条款 | 派活方 |
| `rounds.md` | 各轮交代 | 派活方追加 |
| `delivery.md` | 交回 | 执行方，每轮重写 |

1. 子类型只决定合同骨架；子类型专有的派发与交付条件以任务书为准，生命周期见 2.4。
2. 同一份任务书多轮时，在同一分支追加提交。
3. 存量单文件任务书仍可使用，下次派活时迁移。

## 2. 双方共守

### 2.0 节奏

1. 敏捷：执行方只写代码并推送，派活方只核对与合并，验证一律在后台跑。
2. 执行方与派活方都不被验证速度拖累：合并不等验证，合并后立即推送。
3. 常驻验证每轮快进到它当时能见到的最新提交，按批次验证，不逐提交爬。
4. 合并冲突撤回并打回原线，由执行方合入 main 后重交；验证报红另开修复线，不打回原线、不阻断合并。
5. 验证与派生物生成滞后是正常状态，由常驻验证批量补齐；合并路径上不放任何耗时步骤（见 3.3 第 2 条）。

### 2.1 甲方（派活方）

1. 职责是提需求、定优先级、验收，不是技术负责人。
2. 任务书只写「要成立什么」「怎么算做到」，并列出现成件；未列出而被重复实现的，责任在甲方。
3. 不写「怎么做」。**例外**：架构约束由甲方写死。
4. 细节有分歧而无冲突时，以乙方为准；对错以检查结果为准。
5. 验收只做基本、快速的检查：核对提交与范围、关键改动和已有检查证据，不把交回自述当作检查结果；不亲自重跑整套判据。耗时复现、逐项遍历、反证矩阵与细查写成脚本交后台运行，或单开核对线，不拖住合并与派发。
6. 不写代码：项目代码的改动再小也写成任务书派出，派活方的时间留给合并与验收。**例外**：用户明确要求派活方自己改；shiftboss 自身见 3.1 第 2 条。
7. 需要用户决定或批准的事只用 `shiftboss ask` 登记到简报「待你定」。这是立即返回的登记命令，不是交互式问答；不得另开 Ask／request_user_input、选择框或其他等待用户回复的流程。登记后立即推进其余工作，不反复催答；只有确实依赖该答案的事项待定，不暂停整条主线。需要用户补充的数据或证据（操作步骤、截图、文件、本机现场）用 `shiftboss need` 登记到「待你补充」，同样只搁置依赖它的事项。不得把超时、默认选项或未回复当作批准。
8. 合同与交代只写这条线要做的事与判据，不写名额、并发、负载与其他线的调度状况；资源由派活方与工具调度，执行方不必关注。

### 2.2 乙方（执行方）

1. 实现方式与结构由乙方决定；合同未写死的即归乙方。检查与测试只在 [DONE.md](DONE.md) 第 2 节允许的范围内由乙方决定。
2. 拿不准的自己定，理由写入交回。仅以下情形把相关事项标待议：用户才能定的取舍；须偏离架构约束；证据无法取得；新旧功能冲突无法两全。其余事项继续做，只有剩余事项全被阻塞才停下交回。
   **例外**：判据所需的发布物因常驻验证未通过而缺失，不算证据无法取得；该判据记「待发布后补」，其余条目做完再交回。
3. 任务书前提与事实冲突时，以事实为准并写明冲突。
4. 不得编造：查不到的标未确认；不得放宽或删改断言；不得伪造判据回显。
5. 停下时同样提交并推送。
6. 不在会话里提问或等待回复：派活方不看会话。要裁定的写进交回标待议并推送，其余按第 2 条继续；派活方需用户裁定时按 2.1 第 7 条登记。
7. 关联文档与项目的架构依据（见项目 `README.md`）冲突时以架构依据为准，不改该文档，在交回「文档冲突」一段写明文档路径与冲突处。
8. 新增、修改功能与解决合并冲突都不得让已有功能回退。
9. 不暂停、不终止本线以外的进程（常驻验证、其他执行方）；测量条件做不到时如实记录。
10. 交回与提交说明可用中文或英文。机器读的标记照写：执行状态写 `执行状态：进展／完成／停下` 或 `Status: progress／done／stopped`；待议写「待议」或 `PENDING`；合同状态行只改状态词（`未做`→`完成`／`待议`）。

### 2.3 冲突

1. 交回分支能无冲突合入 main 是执行方的责任（4.1 第 8 步）；hub 拒收与 main 冲突的推送，执行状态为「停下」的除外。
2. 派活方合并时遇到派生物以外的冲突，`shiftboss merge` 自动撤回；派活方不解决冲突，在 `rounds.md` 追加一轮交代打回原线重新合并，不记退回、不算返工。
3. 执行方解决冲突时权威内容逐块解决，不得让任一方已有功能回退；派生物整包取 main 一边，由常驻验证重新生成。
4. 执行方无法确定的冲突取舍交回标待议，在交回写明两边各自的意图。

### 2.4 生命周期

1. 目标须有可达的完成状态：合同各条判据全部成立即做完。
2. 执行方每做完一段即提交推送，接着做下一段；全部条目完成或剩余条目均被具体阻塞时停下。推送一次不算结束。
3. 每个推送的提交各自核对、各自合并；合并不关会话、不归档。
4. 执行方每次推送都在 `delivery.md` 顶部写执行状态：`进展`（接着做）、`完成`（合同条目全部完成）或 `停下`（被具体阻塞、待裁定或建议拆分）；派活方据此决定表头的调度状态与续派、收摊或裁定，不看会话猜。
5. 做偏（产出不再指向合同判据）或分裂（做的过程中发现某一条目实为合同未预见的几件独立的事）时，执行方停下，交回写拆分建议：每份新任务书的目标与判据。合同本就列出的多个条目彼此独立，不算分裂。
6. 派活方把拆分落成新任务书，表头 `来源` 指回原任务书。
7. 派活方核对认定做完或已拆分后，把该线确立的规则写进对应文档，再 `shiftboss.merge --done` 关会话并归档。交回已全部合入、只剩判据「待发布后补」的，当即归档，由派活方在发布后补核，不成立的另开任务书；不为等核对占着执行方会话。核对后决定不合的（如性能线没有可合的改动），分支保留、不合入即归档。
8. 一份任务书最多派 20 轮；到上限 `dispatch` 拒派，按第 6 条拆分。
9. 调度状态（派活方写在表头）与执行状态（执行方写在交回顶部）对称；会话与提交由收件箱现算。

## 3. 派活方

### 3.0 基础设施

0. shiftboss（包与本目录）由派活方维护，每次改动向用户汇报；新协议写进代码，旧协议由派活方手动兜底，兜不住时停用。
1. 派活方只做初步检验、合并与派发，不跑生成、全量测试或打包。派活方会话间的并发由 UserPromptSubmit 钩子仲裁：用户最后对话的派活方会话持有派活权，其余会话的门铃、派活、合并被拒，被拒即退出派活流程。
2. 门铃保持在听：宿主支持流式监听（如 Claude Code 的 Monitor）时，以 `shiftboss bell --ignore-green --heartbeat-minutes 50` 持续接收、每行一条事件，监听到期即重挂；不支持时以 `shiftboss bell --ignore-green --heartbeat-minutes 50` 单独作一条持续后台命令（时限 6 小时）。心跳固定每 50 分钟一次，不因分支推送、自动合入或其他通知顺延；每次响铃后监听器继续运行，不需要重挂；进程意外退出才恢复监听。
   **退出判据**：本轮可处理事项全部办妥，其余事项仅等待执行方交回、发布或用户答复时，立即结束当前回复，让门铃推送唤醒下一轮。后台任务由任务书与收件箱继续追踪，结束当前回复不把任务标为完成。不得为等待新交回调用 sleep、反复读取门铃日志、轮询收件箱或发送重复进度；持续推进任务的要求不要求派活方占住当前轮次。等待执行方交回的验收由已有任务书与收件箱追踪，不另登记「立即可做」的重复待办。
3. 每次收到门铃（含心跳）都读全部输出（含「⚠」行），核对收件箱与简报，并按 3.7 处理本轮可办事项。
4. 门铃挂不上时告知用户，照常用 `inbox status` 核对。
5. 每次回复结束时 Stop 钩子显示 `shiftboss brief`（在办任务、派活方待办、错题、常驻验证三条支线、棘轮余量、性能、门铃、机器），供用户对照后台实际；派活方不必转述。派活方的在途事项一律经 `shiftboss todo` 登记（可带触发条件，满足时门铃响），简报即完整现场，不另写交接文件；要用户批准或决定的事经 `shiftboss ask` 进简报「待你定」。简报首行「该你处理」列出派活方现在就能动手的事项，收尾前逐项处理或说明暂不处理的理由；不空时 Stop 钩子拦下收尾一次。暂不处理的无主工具闸红，登记带条件的待办并在正文写明票据号，即不再计入。
6. 常驻验证由派活方启停与重启，不等用户授权；没在跑时当场拉起。它分三条并行支线，`shiftboss verify start`／`stop` 一并启停：工具闸支线按提交生成、发布、跑测试与闸；页面支线（`shiftboss patrol`）发布前进时先核本批改到的页面，再逐页扫全部页面；定时支线跑构建冒烟等定时重活与自动合入。三条互不让路，检查不设总时长，连续无输出才判卡死。页面红记进门铃但不叫醒，派活方每次醒来看【常驻验证】成批处理；页面红与工具闸红同样处理，归因后开修复线或并入在办线，修好后页面支线扫到即自动消红。每个红页都认领到负责修它的线（`patrol claim`），已由别的线修好的认领到那条线；【常驻验证】里「无人负责」「修复无效」的红页才开新线。发布落后时合入照常，页面支线自动暂停到发布追上（见 `shiftboss.patrol`）；依赖发布物的测试线同样等发布，派发前置写 `publish:<提交>`。红页多时可派 `triage` 任务书由执行方分诊，派活方核实其报告后开线；分诊不代替派活方每次醒来按归属核对当前遍的新红。
7. 项目根缺 `shiftboss.toml` 时由派活方生成：配置项见 `shiftboss.config`，取值从项目 README 提取，提取不到的问用户。
8. 自动触发与后台运行的行为一律登记在 `shiftboss.config.AUTOMATION`，触发前读项目 `shiftboss.toml` 的 `[automation]` 开关，关即不做；开关状态在状态摘要里逐项标在名称后（如【常驻验证：开】），派活方据此判断哪些事会自动发生，不凭记忆。

### 3.1 流程

1. 开工与换会话接手先跑 `shiftboss inbox status` 与 `shiftboss recover --check`。
2. 写任务书，提交并推送。**例外**：shiftboss 自身由派活方直接修改。
3. 派活方自己运行 `shiftboss dispatch`；目标副本须空闲。执行方命令行由插件解析，判断「没装」前先查插件。
4. 各线状态只以收件箱为准，不看进程与会话记录。
5. 做成与否按 [DONE.md](DONE.md) 第 3 节任务书那一列判；派活方只做基本、快速的检查，通常几分钟内结束。先看已有脚本结果、关键日志与提交是否对应；只在能立即完成时补一个定向检查，不因判据多而逐项重跑。需要长时间启动页面、等待生成、完整复现或全面细查的，转脚本、常驻验证或独立核对线并继续主线；已有明确失败或缺失必要证据的如实退回，不以转后台冒充通过。
6. 交代经 `dispatch` 写入轮次记录，只写本轮独有信息与实测数字，不带入核对中读到的实现细节；含反引号、反斜杠、`<>`、`$` 的经 `-F` 传入。
7. 交代列出本轮能做的全部事项；要派活方裁定的写明，并让执行方跳过该项继续。
8. 任务书引用的数字当场重算，复算命令一并写入，并注明对不上以执行方查到的为准。
9. 执行方在做本轮时不追加交代：追加的写进合同或下一轮交代，交回停下后派出。严重影响本轮的，先 `--close`，再重开会话或 `--fresh`。`--recover` 只用于意外中断（断电、崩溃、执行方报错中断等）；挂住超时且试派被拒的线按意外中断处理，用 `--recover` 投「继续」接回。`--close` 前先看副本工作树，有未提交改动的不关；**例外**：副本一小时以上无文件变动的按卡死处理，`--close` 后不加 `--fresh` 续派，交代先收拾工作树里的改动再继续。派活报执行方起不来的，先看它打印的退出前输出：任务书、副本或启动参数的问题要修；查明是执行方自身的问题（如联网超时）的，不深究，按挂住超时同样的节奏稍后重派。同一件事反复失败或拿不准原因的，登记 `shiftboss puzzle`（简报「我的困惑」），写明试过什么、`--line` 列受影响的线；涉及命令失败的附上能复现现场的原样命令与报错首行，每条只写到用户能复现为止；门铃每次响时当即试一次，查明后 `--resolve` 写原因与处理。
10. 合并后即推送；关会话与归档按 2.4。本地有合并提交时同步远端用 `git pull --no-rebase`。
11. 归档的任务书不移回在办：后续另开任务书，表头 `来源` 指向归档的那份。
12. 命令链只用 `&&`；靠退出码判断成败的命令不接管道。

### 3.2 派活方另须决定

1. 执行方按控制目录 `EXECUTORS.md` 第 1 节选；配额即副本数；产能不足时加副本，不靠拆细。
2. 核对参考 `EXECUTORS.md` 第 2 节的已知风险，仍遵守 2.1 第 5 条的快速检查边界；其中耗时的复现转后台或独立核对线，不扩成派活方逐条重跑。该表何时更新由用户决定。
3. 执行方的模型由用户指定，派活方只记录；推理强度由派活方按该线表现在任务书表头「推理强度」调整（low、medium、high、xhigh；不用 max、ultra，它们触发执行方自身的 plan 模式），不写即沿用执行方配置。
4. 改已发布数据的形状时，范围包括消费端；旧断言只许收窄。
5. 两线可能对同一事项作不同决定时，写明写权归属；子树不相交的可以并行。
6. 任务之间的先后写进任务书表头的派发前置与合入前置，不靠记忆；前置任务书归档才算满足，派活与合并入口未满足即拒绝。默认只设合入前置：接口与文字冲突在合入时对齐，缺的前置件由各线自补；只有前一线的产出是本线的输入数据时才设派发前置。
7. 派活时判定表头「破坏性」：会使既有能力不可用的写 `是` 并在合同列出允许失去的能力，其余写 `否`。
   派活时在任务书表头写写入范围（按项目的领域目录）：改公共入口的按调用方清单定，改名的按全仓检索旧名的命中目录定，改默认产物的含闸门里比对该产物的检查，含项目登记的持久证据目录；交回证据留在工作副本的 `out/`，不列入范围、不进提交；合同要求或准许改的文件都在范围内，受保护路径逐个列出；推送与合并时写到范围外即拒收，范围不够由派活方调整。
8. 合同的禁令只写用户或架构定过的事，不自造一刀切的禁令。
   明确改页面布局的线表头写「改布局：是」并把布局基线目录（项目 `[guard] layout_paths`）列入写入范围；其余线改布局基线在推送时拒收。

9. 任务书按表头 `类别` 排优先次序；冲突或资源紧缺时次序在前的先做，派活方按此自行调度，不逐次报告用户：

   | 类别 | 次序 | 派发条件 | 资源紧缺或冲突时 | 结果的有效性 |
   | --- | --- | --- | --- | --- |
   | 架构 | 1 | 随时 | 先占副本与额度 | 有效 |
   | 开发 | 2 | 随时 | 让架构 | 有效 |
   | 修复 | 3 | 随时 | 按被挡住者的类别排；挡住常驻验证生成的按架构排 | 有效 |
   | 核对 | 4 | 随时 | 让前三类 | 清单以交回时的 main 为准 |
   | 性能 | 5 | 随时，同时只开一条 | 最先让出 | 每轮巡检从耗时最长的页面开始检查实际写法；只有确认不合理写法造成高耗时时才修，合理或证据不足则记录依据结束；不默认追加CPU剖析、独立计时、改前改后性能实验或页面矩阵，修改后的必要功能检查仍按影响范围做 |
   | 默认 | — | 未填按开发 | — | — |

10. 执行方会话按配额开满；开发线只跑快速检查，耗时或重度的核对（浏览器、生成、构建、全量扫描）一律归常驻验证或核对线，不在开发线排队限量。
11. 新接入的执行方先派一份 `onboard` 任务书；按 `taskbook new` 回显的参考答案逐题批改，批改结果报用户，作为更新 `EXECUTORS.md` 的依据。

### 3.3 合并

1. 合并冲突按 2.3 撤回并打回原线。
2. 合并即推送，不生成派生物、不跑测试或打包；打开页面等核对放在推送之后。
   任务书表头「改检查」声明本线是否改检查本身（快速检查运行的脚本、已登记测试、测试目录与基线文件），缺省为否：未声明的线改到检查本身在推送时拒收；声明为是的线合并时仍先拒绝，派活方逐项核对是任务书要求、未放松既有断言后以 `--checks-reviewed` 合入。
   同时改了生成器与读取方的线两段合入：先合交回写明的生成器提交，待常驻验证发布越过它再合分支 tip；派生物缺新产物时读取方会在启动即崩。
3. 交回报了文档冲突时，合并后按第 7 节重写所列文档，冲突处改从架构依据；不阻塞派活。
4. 项目在 `shiftboss.toml` 的 `[automerge] subtypes` 登记的子类型，交回满足自动合入条件（见 `shiftboss.automerge`）时由常驻巡检合并、推送并归档；派活方事后读交回，有问题撤回，读完以 `shiftboss automerge --ack` 确认。
4. 验收发现差错时（含派活方自己的），在控制目录 `mistakes.md` 追加一条，格式见该文件开头。条目写进规则文档或代码检查后即从错题本删去，删前的全文留存在控制目录 `mistakes-archive/`。
5. 核对不过就打回，不替执行方补救：记退回、记差错，交代只写「哪里不成立 ＋ 判据」。先查计数口径有没有被绕开（搬文件、改写形式、改清单），再看数字。
6. 新增测试项需用户同意时，按 2.1 第 7 条登记「待你定」，批准后再登记测试（DONE.md 第 2 节第 7 条），其余工作继续；测试与构建线的每项新增，派活方核对必要性：守哪条规则、现有检查为何覆盖不到、同时删去了什么；说不清的打回。反证由执行方脚本或独立核对线完成：临时改回原样应失败，再恢复；派活方快速核对对应回显。
7. 交回引用的日志抽查关键结论、失败项与所对应的提交，不逐份通读或重跑；与交回结论不符即按第 5 条处理。
8. 进展合并按核对过的提交号合并，不按分支最新位置。
9. 界面改动的页面核对由常驻验证的页面闸按本批改动承担；报红按 3.3b 开修复线。
10. 核对规则落实情况先确认规则的计量口径；迁移类除数值不变外抽查来源与名字语义相符。
11. 每清零一类违规，提议一道守住它的检查；经用户审查同意后才登记到合并快速检查或推送守卫，不自动加。新增的检查须能单独运行，不依赖其他检查的结果或执行顺序。
12. 修回归以引入它的提交为单位排查全部改动处。
13. 清单类交回按项目的领域目录分表；派活方只做少量快速抽查，不要求逐领域、逐维度亲自复现。全量审查的独立复核与无问题区域抽查交脚本或单独核对线；报出的问题先快速核对来源与证据，证据不足的交核对线定位，确认后开修复线。发现漏项则补开修复线，并把审查盲区写进下一轮合同。空闲审查的触发与接续按 3.7。
14. 「破坏性」为 `否` 的线，快速抽查交回「受影响的既有能力」的证据；耗时复现交后台或独立核对线。对不上按第 5 条处理。
15. 打回前在项目说明与核心代码里查证判据，不凭「写法像违规」下结论。
16. 执行方「做完了没推」时先读其副本里的交回再续派，不只催推送。
17. 修用户报错的线，核对以复现路径经过用户原始调用栈的帧为准。
18. 全站页面闸失明（大面积回归未修）期间，不合入大范围界面重构。
19. 判「待发布后补」或发布滞后前，先看最近一轮生成是否在该提交上完成；未完成即按生成失败处理。

### 3.3b 常驻验证

1. 停用期间的报告只作历史结果。
2. 报红进入收件箱，不阻断合并。
3. 生成结果在 main 前进后三方合并到最新 main 再发布；两侧都改过的路径本轮不发，由下一轮重算。
4. 派生物是否已发布看报告的 `publication`，不看是否全绿。
5. 超时预算的红归测试与构建线，先查生成与测试是否膨胀；测试与构建线只在没有其他在办线时派活，有在办线时它的票先认领挂起。
   开发线不各自跑例行构建，例行的构建对照由测试与构建线统一做，以免重复；测试与构建线积压的独立事项按事项拆成单独的线并行，判据需要构建的各线自行构建。
6. 生成红挡住整轮验证时，派活方停下引入它的线的当前一段，令其先修再继续。
7. 改了 `verify.py` 须重起常驻验证：`shiftboss verify stop` 后 `shiftboss verify start --publish`。
8. 修了验证器自身而主线没有新提交时，用 `shiftboss verify rerun` 让它重验已验过的提交（先停、后起）。
9. 开修复线前读失败日志：多项失败逐项归类，各类分开开线；任务书列出全部失败项。
10. 验证按批进行，报红只报告、不二分：筛查报告附本批中改过日志所提路径的候选提交，没有命中时列出整批；派活方据报告开 `sweep` 线定位来源，线索明确的直接开修复线。

### 3.3c 检查的两类

| 类 | 特征 | 在哪跑 |
| --- | --- | --- |
| 快速检查 | 秒级；规则简单；只读源码，不依赖派生物与浏览器；能单独运行 | 推送前 `shiftboss check`、合并时 `[merge] fast_commands`；报违规即拒收 |
| 全量核对 | 耗时；全量；依赖派生物、构建或浏览器；要求精确定位 | 常驻验证或低频的核对线（任务书子类型 `sweep`）；报红进收件箱，按 3.3b |

1. 新增检查、或把检查从一类挪到另一类，须经用户审查同意（3.3 第 11 条）。**例外**：快速检查单项实测超过 60 秒的，派活方直接挪进常驻验证的闸（用户已同意），开发线不等它。
2. 检查的 `when` 覆盖它实际扫描的全部目录；只改未覆盖目录的合并不触发它，违规会漏进 main。

### 3.4 拆分

1. 每份任务书须能独立验收。
2. 表头「预计要动哪儿」是提示，不是限制。
3. 旧任务书理清的代价高过重写时就归档，余下的写成新任务书；归档写清状态格的依据，不伪造交回。
4. 进度指标须写明是哪几个数，并指向结构性判据。
5. 修复常驻验证报出的红一律新开会话（`--fresh`）。
6. 执行方始终推不动时，按 2.4 拆分，另开任务书与新会话。

### 3.5 待议

能定的写入该条要求；需用户决定的按 2.1 第 7 条登记，其余照常。判断前快速核对执行方给出的证据；耗时复现交脚本或独立核对线，不等它再处理其他事项。

### 3.6 推进

1. 任务书链自行推进；交付模式、线的定位与 shiftboss 的问题由派活方直接定、直接改，写明理由。
2. 需求是否成立、是否引入新的能力类别需用户决定时，按 2.1 第 7 条登记「待你定」，只搁置依赖该决定的事项，其余工作继续。
3. 把要求归给用户前，沿来源链查用户原话；查不到的写成「派活方定」，向用户提起时说明是推断。
4. 登记选择或设计确认前，对照用户最近定的原则；已有答案的直接执行，不重复请求确认。
5. 用户需求原话有歧义且确实影响取舍时，用一句话写清理解与待定点，登记「待你定」；可独立推进的部分照常派发，不开问答等待。
6. 用户报错缺少必要操作步骤时，先查已有上下文与日志，仍缺的登记「待你补充」；修复范围按用户描述的现象类定，不按首个复现页定，其余可做部分继续。

### 3.7 待办与空闲工作

1. 门铃是唤醒通知，处理范围以当前收件箱、简报、用户已授权的持续事项及自动开关为准；部分执行方在跑不免除派活方处理其余可办事项。
2. 触发后的动作按下表执行，无须用户再次催办或重复授权。

| 对象 | 触发后的处理 |
| --- | --- |
| 条件已满足的待办 | 当轮按正文推进；仅在办妥或剩余工作已转入明确任务书或带真实触发条件的待办后，关闭原待办。 |
| 空闲全项目审查 | `idle_audit` 开启，门铃确认连续两次空闲且 main 自上次审查已前进时，派活方当轮建审查任务书、核对合同、提交推送并派出；建线本身不算派出。 |
| 用户已授权的持续性能排查 | 查看本轮巡检耗时最长的页面，先对照旧结论检查当前源码；写法合理则说明依据并结束，确认不合理写法导致高耗时才安排修复，不因页面仍慢而连续开深入分析或测量线。 |
| 旧提醒或重复通知 | 核对当前台账与提交，已办妥且无新增内容的跳过；仍处理本轮其他可办事项。 |
| 默认 | 在已有授权与开关范围内按类别次序推进；需要新授权或用户取舍的登记为待定，其余照常办理。 |

3. 暂不推进须写明具体阻塞或所缺新证据，并登记能解除它的触发条件；不能只因事项属于空闲工作或本轮门铃未点名它而延后。
4. 上述处理完成后按 3.0 的退出判据结束回复；接续要求不构成为等条件成立而轮询或占住当前轮次的理由。

### 3.8 断电／崩溃

派活方会话恢复时，钩子跑 `recover` 拉起各线，派活方按 3.0 重挂门铃、恢复基础设施；拉起不是核对。

## 4. 执行方

### 4.1 流程

1. `git fetch origin`；任务书以 `origin/main` 上的为准。
2. 从 `origin/main` 的 `shiftboss/plans/<名字>/meta.json` 取「你的工作副本」与「分支」。当前目录与「你的工作副本」不符才停下；不在该分支、工作树里没有任务书都不是停下的理由。
3. 切到该分支（远端没有就从 `origin/main` 建），合入 `origin/main`；`dispatch` 回显已切好并合过的跳过。
4. 读 `contract.md` 与 `rounds.md`；`rounds.md` 末条为本轮交代。
5. 按 `meta.json` 的 `完成标准` 查 [DONE.md](DONE.md) 第 2 节同名列：只做「必须」「是」的动作。
6. 按合同「要做的事」做到要求写明的形态为止，不多不少；想到的扩展写进交回作建议。推进、停下与拆分按 2.4。
   表头「破坏性」为 `否` 时不得减少任何既有能力，不减少就做不成的停下标待议；为 `是` 时只可失去合同「允许失去的能力」所列，逐条在交回报告。
7. 测试与构建线新增常驻测试在同一段内登记到 `shiftboss.toml` `[regen] plan` 的对应 gate。
8. 交回前再 `git fetch origin` 并合入 `origin/main`，解决冲突；合入触及本线判据的，在合入后的代码上重跑。
9. 交回引用的每份回显须出自最终代码，并覆盖交回所述的全部项；生成回显的临时脚本与回显一并留在证据目录，供派活方复现。
10. 写 `delivery.md`（顶部写执行状态），过 `shiftboss check`（与合并时同一套快速检查），提交并推送。与 main 冲突的推送会被 hub 拒收，「停下」除外。
   推送回显列出认领给本线的红时，下一段先修它们。
11. 引用的任务书用 `shiftboss taskbook show <名字>` 读，在办与已归档都可找到。

### 4.2 卡住

1. 做不到的不绕过：交回写明卡点并标待议，其余条目照常完成。
2. 卡点报告立即推送。
3. 禁令与正确结果冲突时标待议。

### 4.3 写权

1. 只写 `delivery.md`；`contract.md` 中只可改各条状态行的状态词。
2. 发布数据是权威；页面与之不符时，默认页面有误。
3. 需改动表头「允许改动的范围」之外的内容时直接改，交回中注明；越出「写入范围」的改动被推送守卫拒收，不绕过，交回写明要加的路径与理由并标待议。
4. 不改 shiftboss（包与本目录）；需要改时停下，在交回写明要改什么、为什么。
5. 不跑派生物生成、不提交派生物：派生物只由常驻验证生成与发布；在编辑器里构建 ROM 不受此限。
   同时改了生成器（项目 `[merge] producer_paths`）与读取派生物的代码时，生成器改动单独成一个提交并在交回写明其提交号；读取方须等发布物带上新产物后才能合入（`shiftboss merge` 据此拒绝）。生成器改动不改变产物的，交回附逐字节对照，派活方以 `--outputs-unchanged` 合入。
6. 交回引用的回显、截图与转储放在 `out/<任务书名>/` 或 `out/<子目录>/<任务书名>/` 下，归档时整目录删除；干净检出与只为一次核对存在的大体积中间产物放系统临时目录，目录名含任务书名，用完即删。
7. 项目说明登记的共用验证现场（存档、即时存档等）按项目说明的缓存位置取用与生成，不放 `out/`，不随归档删除。
8. 表头「关联在办线」列出的线，可只读查询其会话了解改动范围与进度；不据此改变本线范围，不依赖其未合入的改动，需协调的写进交回。

## 5. 通用

1. 判据须能区分做成与没做成；新检查须反证：改回原样应失败。
2. 范围按需改动的文件倒推，含消费端。
3. 继承的前提须重新核实。
4. 复核走另一条独立路径。

## 6. 通用开发约束

各项目沿用；项目只在自身说明里补具体路径与口径。

| 约束 | 规则 | 落实 |
| --- | --- | --- |
| 不减能力、不留兼容 | 改动默认不减少既有能力；靠同一提交把调用方与数据改到新形，不写兼容层、适配层、迁移别名或双写；确需失去的能力逐条列出 | 表头「破坏性」（3.2 第 7 条） |
| 依赖显式 | 用到的依赖写在自身声明里、经明文接口取得；不靠全局预载、全量登记或调用方顺带准备；缺声明即报错，不静默回退 | 项目登记的显式依赖检查 |
| 修在共用处 | 同类缺陷修在共用部件上，不逐页补丁；改共用部件列出全部使用方 | 合同（TEMPLATE 第 3 节第 13 条） |
| 退化归因 | 修复交回写引入提交与归类：他处改动击穿本处（架构问题）或同一功能内改动失误（执行问题） | 合同（TEMPLATE 第 3 节第 19 条） |
| 检查不由被检者改 | 检查脚本、已登记测试与基线只许表头「改检查：是」的线改；基线只减不增 | 推送守卫、合并检查（DONE 第 2 节） |
| 布局固定 | 页面布局以几何指纹基线固定；改布局须表头「改布局：是」并同提交更新基线 | 推送守卫 `[guard] layout_paths`、页面闸 |
| 冻结 | 定型模块列入受保护路径，改动须任务书写入范围逐个授予 | 推送守卫 `[guard] protected` |
| 生成输入 | 改到生成输入的线推送前在全新检出只跑受影响的生成阶段 | `shiftboss regen --branch-check`、合并核对 |
| 页面验收 | 开发线只点名少量路由与交互样本，不跑页面矩阵；全量与影响面由常驻验证核对；未通过的在 main 同负载对照，与 main 相同的认可 | 合同（TEMPLATE 第 3 节第 20 条） |
| 说明的去处 | 机制解释、限制说明、实现取舍与未确认项写进交回；界面只放用户操作所需的名称、值与状态（不可写原因进选择器状态栏），代码注释按第 7 节写法 | 合同、派活方合入时核对 |
| 看图 | 布局判据先用页面闸的 JSON（几何、指纹、就绪状态）；截图只在判据需要视觉判断时查看，一轮内集中在末尾看 | 带图会话下一轮开新会话（`shiftboss dispatch`） |
| 共用主机 | 重度验证不放开发线；开发线浏览器核对并发 1；不设全机浏览器名额；耗时不设硬门槛，卡死按无进展判；页面核对、巡检与性能工作让开发线：页面核对前等 1 分钟负载低于 20（最多 60 分钟，仍不满足则与 main 同负载对照），巡检与定时项在高负载时暂停 | DONE 第 2 节、常驻验证（`patrol.HIGH_LOAD`） |
| 快速检查轻量 | 合入时的快速检查单项超过 60 秒移入常驻验证 | 3.3c |
| 推理强度 | 派活方按该线表现调整执行方推理强度 | 表头「推理强度」（3.2 第 3 条） |

## 7. 写法

适用于新写与修改的文档、任务书、交回与代码注释。**例外**：归档不追改；存量文档的写法与术语在下次修改时一并改。

1. 写成条款：一条一句，只写规则。
2. 规则须自解释；只有例外或歧义才加说明，且只说明例外本身。
3. 同一内容只写一处，其余引用。
4. 不写经过：日期、次数、线名、「曾经」不入文档。
5. 不写工具用法；工具细节写在工具自身，文档只写用途。
6. 不重述：已写明的规则不再附解释、举例或强调。
7. 自查：删去任一句后规则不丢失，则删去。
8. 按对象不同的规则写成表格：每行一类对象，末行「默认」管未登记与新增的；不写泛泛条款。
9. 术语以项目架构依据的术语一节为准。
10. 归档以外的文档始终有效：引用的路径、接口与事实一失效即改。
11. 代码层面的术语（语法、API、类型与工具名，如 try/catch、Proxy、capture）写原文，不译。
