# 代理协作工作流

Git Feature Branch Workflow：派活方负责初步检验、合并与派发，后台设施按第 3.0 节启停。**红不阻断合并。**
本文档只写规则；项目专有内容见项目文档，工具细节见工具自身。

## 0. 工具

本目录由 `shiftboss` 包安装进项目（`shiftboss.toml` 的 `docs_dir`，缺省 `docs/shiftboss/`），不在此处修改；改动在包内 `docs/` 做，`shiftboss bootstrap` 同步，`--check` 报出不一致。
项目专有的约定（架构依据、文档写法、测试目录、证据目录、完成标准的不放松清单）见 `AGENTS.md` 指向的项目文档。
家目录：项目旁的 `<项目名>.shiftboss/`（`shiftboss.toml` 的 `copies_dir` 可改），放 bare 仓库 `hub.git`、全部执行方副本（`<执行方><序号>`）与验证工作区 `verify/`。
控制目录：家目录下的 `control/`（`shiftboss.toml` 的 `control_dir` 可改），放仅派活方读写的私有文档（执行方评估 `EXECUTORS.md`、错题本 `mistakes.md`）、台账、配额、门铃与验证报告；工作副本内不存放、不链接。

| 入口 | 用途 |
| --- | --- |
| [`TEMPLATE.md`](TEMPLATE.md)、[`templates/`](templates/) | 任务书格式与各子类型骨架 |
| [`DONE.md`](DONE.md) | 完成标准：段内能做什么、怎么算做成 |
| `shiftboss taskbook` | 建、查、迁移任务书；任务书结构只由它解析 |
| `shiftboss dispatch` | 派活、写入交代、关会话、设配额 |
| `shiftboss inbox` | 各线状态与验证状态的唯一来源 |
| `shiftboss merge` | 合并；`--done` 关会话并归档 |
| `shiftboss verify` | 常驻验证：生成、全量测试、打包、归因、报红 |
| `shiftboss recover` | 断电／崩溃后拉起各线 |
| `shiftboss bell` | 推送通知 |
| `shiftboss bootstrap` | 准备 bare、工作副本、钩子与本目录文档 |
| `shiftboss regen` | 分层生成；产物名单由生产端经 `shiftboss.outputs` 声明 |

## 1. 对应关系

| 标准流程 | 本工作流 |
| --- | --- |
| issue | 任务书 `docs/plans/<动词>-<对象>/` |
| feature branch | `codex/<任务书名>` |
| checkout | 工作副本，一份任务书独占一个 |
| pull request | 交回 `delivery.md` |
| code review | 核对：派活方重跑判据 |
| CI | 常驻验证 |
| 关闭 issue | 归档至 `docs/plans/archive/` |

### 1.1 任务书

| 文件 | 内容 | 写权 |
| --- | --- | --- |
| `meta.json` | 表头事实 | 只经工具修改 |
| `contract.md` | 合同，含「派发与交付」条款 | 派活方 |
| `rounds.md` | 各轮交代 | 派活方追加 |
| `delivery.md` | 交回 | 执行方，每轮重写 |

1. 子类型只决定合同骨架；子类型专有的派发与交付条件以任务书为准，生命周期见 2.4。
2. 同一份任务书多轮时，在同一分支追加提交。
3. 存量单文件任务书仍可使用，下次派活时迁移。

## 2. 双方共守

### 2.0 节奏

1. 敏捷：执行方只写代码并推送，派活方只核对与合并，验证一律在后台跑。
2. 执行方与派活方都不被验证速度拖累：合并不等验证，合并后立即推送。
3. 常驻验证每轮快进到它当时能见到的最新提交，按批次验证，不逐提交爬。
4. 合并冲突快速合并后另开冲突线；验证报红另开修复线。两者都不打回原线、不阻断合并。
5. 验证滞后是正常状态；派生物因此可能旧一轮。

### 2.1 甲方（派活方）

1. 职责是提需求、定优先级、验收，不是技术负责人。
2. 任务书只写「要成立什么」「怎么算做到」，并列出现成件；未列出而被重复实现的，责任在甲方。
3. 不写「怎么做」。**例外**：架构约束由甲方写死。
4. 细节有分歧而无冲突时，以乙方为准；对错以检查结果为准。
5. 验收时自己重跑判据，不采信自述。

### 2.2 乙方（执行方）

1. 实现方式与结构由乙方决定；合同未写死的即归乙方。检查与测试只在 [DONE.md](DONE.md) 第 2 节允许的范围内由乙方决定。
2. 拿不准的自己定，理由写入交回。仅以下情形停下标待议：用户才能定的取舍；须偏离架构约束；证据无法取得。
3. 任务书前提与事实冲突时，以事实为准并写明冲突。
4. 不得编造：查不到的标未确认；不得放宽或删改断言；不得伪造判据回显。
5. 停下时同样提交并推送。
6. 关联文档与项目的架构依据（见 `AGENTS.md`）冲突时以架构依据为准，不改该文档，在交回「文档冲突」一段写明文档路径与冲突处。

### 2.3 冲突

1. 冲突不打回原线：执行方照常做本轮并在交回写明。
2. 派活方当场取简单方案合并：选定一边，落选一边以带 `CONFLICT-KEPT` 的注释保留并写明取舍；提交推送后另开 `conflict` 任务书派出复核与修复。合并不因冲突停下。
3. 冲突线内，权威内容逐块解决；派生物整包取一边，由常驻验证重新生成。
4. 冲突线内仍无法确定的，保持 `CONFLICT-KEPT` 注释并交回标待议。

### 2.4 生命周期

1. 目标须有可达的完成状态：合同各条判据全部成立即做完。
2. 执行方每做完一段即提交推送，接着做下一段；全部条目完成或剩余条目均被具体阻塞时停下。推送一次不算结束。
3. 每个推送的提交各自核对、各自合并；合并不关会话、不归档。
4. 执行方每次推送都在 `delivery.md` 顶部写执行状态：`进展`（接着做）、`完成`（合同条目全部完成）或 `停下`（被具体阻塞、待裁定或建议拆分）；派活方据此决定表头的调度状态与续派、收摊或裁定，不看会话猜。
5. 做偏（产出不再指向合同判据）或分裂（做的过程中发现某一条目实为合同未预见的几件独立的事）时，执行方停下，交回写拆分建议：每份新任务书的目标与判据。合同本就列出的多个条目彼此独立，不算分裂。
6. 派活方把拆分落成新任务书，表头 `来源` 指回原任务书。
7. 派活方核对认定做完或已拆分后，把该线确立的规则写进对应文档，再 `shiftboss.merge --done` 关会话并归档。
8. 一份任务书最多派 20 轮；到上限 `dispatch` 拒派，按第 6 条拆分。
9. 调度状态（派活方写在表头）与执行状态（执行方写在交回顶部）对称；会话与提交由收件箱现算。

## 3. 派活方

### 3.0 基础设施

0. shiftboss（包与本目录）处于维护阶段：改动只由派活方做，每次改动及时向用户汇报；新协议写进代码，旧协议由派活方手动兜底，兜不住时停掉旧的、用新的跑。
1. 派活方只做初步检验、合并与派发，不启动生成、全量测试或打包来替代常驻验证。
2. **被任何事件唤醒后先重挂门铃，再干别的**：
   `shiftboss bell --once --ignore-green --heartbeat-minutes 120`。
   它每响一次就退出；忘了重挂，推送照常进来而派活方一无所知。
   **单独起一条后台命令**——折进带 `&` 或重定向的复合命令里，起的进程不受跟踪，退出时叫不醒人。
3. 门铃与常驻验证没在跑时 `inbox status` 会报出来；`dispatch` 的回显也报门铃。
4. 重挂门铃后读它的全部输出（含「⚠」行），再跑 `inbox list`，处理其中全部「可核对」，不只处理门铃点名的那条。
5. 常驻验证由派活方启停与重启，属合并核对的常规流程，不等用户授权；没在跑时当场拉起。

### 3.1 流程

1. 开工与换会话接手先跑 `shiftboss inbox status` 与 `shiftboss recover --check`；状态从 hub 的分支与任务书现算，不依赖会话记忆。
2. 写任务书，提交并推送。**例外**：shiftboss 自身由派活方直接修改，不派。
3. 派活由派活方自己运行 `shiftboss dispatch`，不交给用户；目标副本须空闲。执行方命令行不在 PATH 上是常态，由执行方插件解析，判断「没装」前先查插件。
4. 各线状态只以收件箱为准，不看进程与会话记录。
5. 做成与否按 [DONE.md](DONE.md) 第 3 节任务书那一列判；核对只重跑判据点名的检查、回显与反证（分钟级以内）。测试套件、生成、打包归常驻验证，派活方改 shiftboss 时同样只做语法检查。
6. 下一轮交代不得带入核对中读到的实现细节。
7. 合并后即推送，不等验证；关会话与归档按 2.4。
8. 归档的任务书不移回在办：后续开发或未了结的待议另开任务书，表头 `来源` 指向归档的那份。
9. 交代经 `dispatch` 写入轮次记录，只写本轮独有信息与实测数字；派活提示词不写任何内容。含反引号、反斜杠、`<>`、`$` 的交代写成文件经 `-F` 传入。
10. **交代的步长要给足**：列出本轮能做的全部事项让它顺着做下去，
   只在全部完成或剩余事项都被具体阻塞时停；不写「本段做 X」把它切成一件。
   要派活方裁定的写清楚、让它**跳过那一项继续做别的**，不要停下等。
11. **任务书里引用的每个数字当场重算**，不复用本会话早前算出的结果；
    复算命令一并写进任务书，并写明「这是上一轮的结论不是证据，对不上以你查到的为准」。
12. **执行方在做本轮时不追加交代**：追加的要求写进任务书（合同或下一轮交代），等它交回停下后作为新一轮派出（`dispatch` 在执行方未停下时拒派）。严重影响本轮的，先 `--close` 停下，再决定重开会话还是 `--fresh`。「继续」只用于意外中断（断电、崩溃、额度用尽）后的 `--recover`。

### 3.2 派活方另须决定

1. 执行方按轮选，按控制目录 `EXECUTORS.md` 第 1 节；配额即该执行方的副本数；产能不足时加副本，不靠拆细。
2. 核对按控制目录 `EXECUTORS.md` 第 2 节多查；该表何时按错题本更新由用户决定。
3. 执行方的模型由用户指定，派活方只记录。
4. 改已发布数据的形状时，范围包括消费端；旧断言只许收窄。
5. 两线可能对同一事项作不同决定时，写明写权归属；子树不相交的可以并行。

### 3.3 合并

1. 合并冲突按 2.3 当场取一边合并推送、再开 `conflict` 任务书，不停下、不打回该线；仅在工作流自身升级时停下。
2. 派生物随合并进入 Git，常驻验证停用期间不自动补齐，陈旧状态须如实保留。
3. 交回报了文档冲突时，合并后按项目的文档写法规则（见 `AGENTS.md`）重写所列文档：冲突处改从架构依据，连同精简与换术语，提交推送；重写不阻塞派活。
4. 验收发现差错时（含派活方自己的），在控制目录的 `mistakes.md` 追加一条，标出出错的执行方、模型与推理档位；只记差错，格式见该文件开头。
5. **核对不过就打回，不替执行方补救**：记退回、如实记差错、交代只写「哪里不成立 ＋ 判据」，不写实现。
   替它补救会让执行方评估失真。**先看计数口径有没有被绕开**（搬文件、改写形式、改清单），再看数字。
6. **新增的合同派活方要自己反证一次**：把那处修复临时改回原样 → 跑该合同 → 确认它**真的失败** → 再改回来。
   不能失败的合同守不住任何东西；「它说验过」和「我验过」是两回事。
   **反证脚本本身会给假结果**——看到「反证时仍然通过」，先确认文件真的被改了（`git status --short <文件>` 非空），再谈合同有没有用。

### 3.3b 常驻验证

1. 停用期间的报告只作历史结果，不代表当前提交已验证。
2. 常驻验证恢复后，报红进入收件箱且不阻断合并。
3. 生成结果在 main 前进后三方合并到最新 main 再发布；两侧都改过的路径算冲突，本轮不发，由下一轮重算。
4. 「验证全绿」不等于「派生物已发布」；派生物是否到 main 看报告的 `publication`。
5. 改了 shiftboss 的 `verify.py` 要重起常驻验证才生效：`shiftboss verify stop` 等当前提交验完后停，急用时 `stop --now`；再 `shiftboss verify start --publish`（工作区缺省为副本目录下的 `verify/`）。

### 3.4 拆分

1. 每份任务书须能独立验收。
2. 表头「预计要动哪儿」是提示，不是限制。
3. **一份旧任务书理清的代价高过重写时就归档**，还值得做的写成新任务书，
   不在旧的上面改来改去——旧的轮次记录、自立的判据与跑偏的指标会一起被继承。
   归档要写清状态格的依据，不伪造执行方的交回。
4. **进度指标必须指向结构性判据**，不能留空让执行方拿取证计数去填；
   合同里出现「按指标推进」「指标未前进即停」而没有一句说清指标是哪几个数，就是个洞。
5. **修复常驻验证报出的红一律新开会话**（`dispatch <修复任务书> --fresh`），
   不把交代投回当初做这件事的那个会话：带着「我当初为什么这么写」的立场看自己的 bug，
   比中立地读一份问题描述更难聚焦。同一份任务书的返工最容易顺手投回旧会话。
6. 执行方始终推不动时，按 2.4 拆分，另开任务书与新会话。

### 3.5 待议

能定的写入该条要求，定不了的保留，其余照常；判断前先复现乙方给出的证据。

### 3.6 推进

任务书链自行推进。交付模式、线的定位与 shiftboss 自身的问题由派活方直接定、直接改，写明理由；需求本身是否成立、是否引入新的能力类别，须问用户。

### 3.8 断电／崩溃

先恢复 3.0 的基础设施，再拉起各线。不做现场检查；拉起不是核对。

## 4. 执行方

### 4.1 流程

1. 先 `git fetch origin`。**任务书在 `origin/main` 上，不在当前工作树里**：
   新开的线、改过表头的线，都要取到 `origin/main` 才读得到。
2. 从 `origin/main` 读这份任务书的 `meta.json`（`git show origin/main:docs/plans/<名字>/meta.json`），
   取出「你的工作副本」与「分支」。**不要用工作树里那一份判**——旧分支上它可能根本不存在。
3. 比对当前目录与表头的「你的工作副本」：**路径对不上才停下**。
   工作树里没有这份任务书、当前在别条分支、目录内容不像这条线，**都不是停下的理由**。
4. 切到表头的「分支」，远端没有就从 `origin/main` 建。**副本停在别条分支是常态**：
   副本轮换使用，上一条线留下的分支还在，切分支与同步都是执行方份内的事。
   **正常派活时 `dispatch` 已经替你切好并合过**（工作树脏或切失败时不动副本），
   回显会说明它做到了哪一步。
5. **一轮只在开始时同步一次**：把 `origin/main` 合入本分支（`dispatch` 回显已合过就不再合），再读 `contract.md` 与 `rounds.md`；`rounds.md` 末条为本轮交代。
   本轮内不再合 `origin/main`；下一轮开始时再按本条同步一次。
6. 读 `meta.json` 的 `完成标准`，打开 [DONE.md](DONE.md) 第 2 节同名那一列；段内检查只做该列为「必须」「是」的动作，为「否」的一律不做。
7. 按合同「要做的事」执行，判据只跑归执行方的部分；推进、停下与拆分按 2.4，另按「派发与交付」条款。
8. 新增常驻测试同一段内登记到生成计划（`shiftboss.toml` 的 `[regen] plan`）的对应 gate，未登记的合并会被拒绝。
9. 写 `delivery.md`（含 2.4 第 4 条的执行状态），提交并推送本分支；已交付的内容须保留。

### 4.2 卡住

1. 做不到的不绕过：交回写明卡点并标待议，其余条目照常完成。
2. 卡点报告立即推送。
3. 禁令与正确结果冲突时标待议。

### 4.3 写权

1. 只写 `delivery.md`；`contract.md` 中只可勾选各条状态。
2. 发布数据是权威；页面与之不符时，默认页面有误。
3. 需改动预计范围之外的内容时直接改，交回中注明。
4. 不改 shiftboss（包与本目录）；需要改时停下，在交回写明要改什么、为什么。

## 5. 通用

1. 判据须能区分做成与没做成；新检查须反证：改回原样应失败。
2. 范围按需改动的文件倒推，含消费端。
3. 继承的前提须重新核实。
4. 复核走另一条独立路径。
