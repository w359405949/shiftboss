# 完成标准

一件活做到什么程度算完。共五列：原型、成形、堆叠、收敛、维护。

## 1. 查哪一列

1. 列名就是任务书 `meta.json` 里 `完成标准` 的值。
2. 这次改动碰到项目文档（见项目 `README.md`）「完成标准」一节的「不放松清单」里的事时，碰到的那部分查「维护」列。
3. 其余全部查 `meta.json` 写的那一列；不看别的列。
4. 用户宣布项目改用哪一列；派活方按项目说明「完成标准」给每份任务书写列名。

## 2. 执行方：段内做什么

开发线以实现业务代码为主，业务目录与文件不划分实例独占写权；生成器源码亦按业务代码处理，运行生成仍遵守下文判据。检查脚本、测试、检查辅助模块与基线统一属于检查代码，须由main上任务书「改检查：是」授权；不再另列受保护目录或逐文件清单，旧「写入范围」不作权限闸。布局基线亦属检查代码；新增测试的审批及合并审阅规则保持。

| 动作 | 开发线 | 测试与构建线 |
| --- | --- | --- |
| 推送前过 `shiftboss check`（共同结构守卫与任务书清单命中的前台快速检查） | 必须 | 必须 |
| 改了界面：打开页面看改动处 | 否（常驻验证的页面闸按本批改动打开受影响页面；合同点名的复现判据照做） | — |
| 开发中临时写脚本定位实际问题，用完不提交；不扩为验收、严格类型或反例矩阵 | 是 | 是 |
| 改了代码段字节：同一交回把核对回显写进该代码段的审定记录，更新审定摘要（`out/` 归档即删，回显不能只留在那里）；审定由改动线自己完成，派活方合入即认可，不另等签发 | 必须 | 必须 |
| 新写检查脚本、探针、常驻测试，提交证据文件 | 否 | 经用户同意（第 7 条）；每项写明守哪条规则、现有检查为何覆盖不到，并列出同时删去的 |
| 跑相关的现有测试 | 仅表头「专项检查」声明的入口与范围；如指定页面闸不超过 3 条路由、并发 1，不跑页面矩阵 | 是 |
| 跑全量测试、派生物生成、打包 | 否 | 否 |
| 检查失败后不改任何东西原样再跑 | 否 | 否 |
| 为让检查变绿去放宽断言、延长超时、加重试 | 否 | 否 |
| 删去合同未写明要删的可见项或可编辑项 | 否 | 否 |

1. 本表为「必须」的，合同没写也做；为「否」的，合同写了也不做，交回「与任务书的偏差」写出判据条号与本表那一行。
2. 开发线发现缺测试、检查或生成改动，写进交回，由派活方转交测试与构建线；临时取证脚本与长期判据按 README 5.1 分开，不能因清理临时脚本而退回人工逐轮核对。
3. 派生物生成、全量测试、打包只由常驻验证做。**例外**：合同判据点名在 Mesen 中实测编辑效果时，可在编辑器里构建并导出 ROM／SAV；子类型为 `perf` 的线默认只读现有巡检记录并审查源码，不追加生成与测量；仅合同另有具体必要判据时，可在自己副本生成核对该项，子类型为 `sweep` 的线可在自己副本里跑生成做读取记录与全量核对；合同明确要求核对生成器产物的线可在全新检出里跑生成核对产物不变或新产物成立；以上是合同明确要求的专项生成取证许可，不是普通开发线的推送或合入前置；普通生成输入改动只交源码，由常驻验证按批生成、发布并保留真实失败。`shiftboss check` 与正常合并不计算生成闭包、不索取分支生成回执。旧任务书若要求每批先生成通过才推送／合并，该前置以本条为准取消；不把未执行或旧源记录报成新源生成通过。专项产物都不提交。
4. 测试每条规则只验一个样本：抽查一份真实数据，或一份覆盖全部字段改动的合成样本；不逐条遍历真实数据。
5. 界面只做语法检查与合并前查看；常驻验证只跑不依赖界面、可在命令行直接运行的检查。
6. 常驻测试的范围与深度以项目架构依据中的分层策略表（验证列）为准：表外不加，未登记的模块按表中「默认」行。
7. 新增测试项（测试文件、用例、闸，或测试目录外的测试框架导入）须先经用户同意，由派活方登记到 `shiftboss.toml` 的 `[verify] approved_tests`；未登记的新增在 `shiftboss check`、hub 推送与合并时被拒，撤回后再推。
8. 「快速检查」控制交付守卫，「专项检查」控制执行方额外检查；后者默认不做，合同点名而清单未列的由派活方补录，执行方先交其余结果，不自行加严。现成同源回执复用；后台完整检查仍独立运行，红不自动成为转写任务的完成前置。

## 3. 派活方：怎么算做成

本节规定完成所需的证据，不要求派活方亲自重跑。派活方只做基本、快速的检查；页面交互、逐项对照、耗时复现与全面核对由执行方的定向检查、脚本、常驻验证或独立核对线提供证据，按 README 2.1 第 5 条处理，不堵住合并与派发。

| 事项 | 原型 | 成形 | 堆叠 | 收敛 | 维护 |
| --- | --- | --- | --- | --- | --- |
| 界面改动 | 对应提交的定向页面检查有结果，派活方快速核对证据 | 同左 | 同左 | 同左 | 同左 |
| 可见项与可编辑项 | 逐项对照改动前后，有合同未写明的删减即不算做成 | 同左 | 同左 | 同左 | 同左 |
| 其余改动 | `shiftboss check` 回显通过 | 同左 | 同左 | 同左，且常驻验证全绿 | 同左，常驻验证全绿，且实测受影响的已发布功能 |
| 合同判据可以要求的动作 | 第 2 节该线所在列为「必须」「是」的 | 同左 | 同左 | 同左 | 同左 |
| 出现新红 | 挡住在办线才开 `repair`，其余留着 | 挡住在办线才开 `repair`，其余留着 | 挡住在办线才开 `repair`，其余留着 | 每条都开 `repair`，清零才发布 | 每条都开 `repair`，清零才发布 |
| 旧版本的用户数据 | 丢弃 | 丢弃 | 丢弃 | 丢弃 | 保留或迁移 |

## 4. 派活方：选哪一列

| 列 | 什么时候选 | 优先 | 可以牺牲 |
| --- | --- | --- | --- |
| 原型 | 形态未定，先把功能做出来 | 功能点尽快出现 | 结构、测试、已有功能的质量 |
| 成形 | 结构未定或正在迁移 | 结构对齐 | 已有功能的质量暂时退化 |
| 堆叠 | 结构已定，功能待补 | 功能点的数量与可用 | 边角缺陷、性能、打磨 |
| 收敛 | 功能冻结，准备发布 | 正确与稳定 | 新功能 |
| 维护 | 已有发布版 | 不破坏已发布的行为与用户数据 | 开发速度 |
